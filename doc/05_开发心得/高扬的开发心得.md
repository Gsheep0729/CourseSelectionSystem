### 1.制定任务计划

### 2.碰壁....

我面临的问题是：项目使用了C++23的模块（Modules）语法，但是pqxx库可能并不兼容模块化（因为它是传统的头文件库）。我希望在基础设施层（Infrastructure）使用传统的头文件方式封装pqxx，而其他层（如领域层、应用层等）仍然使用模块。这样，既可以使用pqxx，又可以享受模块带来的好处。

### 3.解决方案

将数据库操作封装在一个独立的库中，这个库使用传统的头文件方式（即.cpp和.h文件），然后被主项目（使用模块）链接。具体来说，可以将数据库连接、代理等基础设施层的代码实现为传统的头文件/源文件，然后通过一个模块接口单元（module interface unit）来导出这些类，使得其他模块可以使用

#### **关键注意事项 **

**Modules 与传统库**：当使用 C++20/23 Modules 时，包含像 libpqxx 这样的传统库，最安全的方法是在 Global Module Fragment (module; 和 export module ... 之间) 
   中包含头文件。 
**TU-local 实体暴露**：GCC 15 非常严格。如果您的模块接口导出了一个类，该类**不能**拥有来自 Global Module Fragment 
   中定义在匿名命名空间或特定模板实例化的成员变量（因为这被视为暴露了 Translation Unit 本地的实体）。F 
**解决方案**：不要在导出的类中持有 pqxx 的类型成员（如 pqxx::connection）。可以使用t 
     PIMPL（指针指向不完全类型），或者像本例一样，在每次操作时创建临时连接（短连接），或者使用 std::any / void* 等类型擦除技术。  

**编译命令**：

## 开发v3.0版本时的心得：架构重构与去SQL化

在 v2.0 完成了数据库的基本连接后，我审查代码时发现了一个严重的问题：`SystemController` 正在变成一个“上帝类”。

### 1. 发现“坏味道”

之前的实现中，Controller 层充斥着大量的原生 SQL 拼接字符串。

```cpp
// ❌ 典型的错误示范
void enrollStudent(string sId, string cId) {
    m_db.execute("INSERT INTO enrollments..."); // 业务层直接操作数据库，这是架构大忌！
}

```

这导致了两个后果：

1. **业务逻辑泄露**：选课容量判断、重复选课校验等逻辑混杂在 SQL 执行流程中，导致领域模型（Domain Model）变得“贫血”。
2. **维护成本极高**：一旦数据库表结构变更，所有 Controller 代码都要重写。

### 2. 实施“手术刀式”重构

我决定严格执行四层架构，将 Controller 回归为纯粹的“协调者”。

* **引入 Proxy 模式（数据访问层）**：
实现了 `StudentProxy` 和 `CourseProxy`。现在 Controller 只需要调用 `findById` 或 `save`，完全不需要关心底层的 INSERT/UPDATE 语句。
* **领域层下沉**：
将“判断是否时间冲突”、“建立内存关联”的逻辑封装进 `Student::enrollIn()` 和 `Timeslot::overlaps()`。
* **消除依赖**：
利用 `std::optional` 处理空值，利用异常处理业务错误，而不是让 SQL 错误直接崩坏程序。

### 3. 踩坑记录

在重构过程中，最大的痛点是 C++23 Modules 的依赖管理。当我在 `app.controller.cppm` 中同时尝试导入标准库和导出带有 `std::unique_ptr` 成员的类时，GCC 15 频繁报错。这迫使我重新审视了模块的导出策略，最终通过合并部分 Infrastructure 模块解决了循环依赖问题。

## 开发v4.0版本时的心得：与编译器博弈（静态库隔离）

这个版本是开发过程中最痛苦、但也最有技术含量的阶段。可以称之为“Pre-v3.0”的噩梦终结版。

### 1. 核心困境：Modules 与传统库的冲突

项目使用了最新的 **C++23 Modules**，但底层的 `libpqxx` 依然是传统的头文件库。当我尝试在模块接口（`.cppm`）中 `#include <pqxx/pqxx>` 时，GCC 编译器彻底崩溃了：

* **现象**：出现 `Internal Compiler Error (ICE)` 或 `Segmentation Fault`。
* **原因**：模块扫描器在处理包含非 ASCII 字符路径（中文路径）以及极其复杂的模板实例化导出时，存在 ABI 兼容性 Bug。

### 2. 架构突围：PIMPL 模式与静态库隔离

为了解决这个问题，我不得不走了一条“曲线救国”的路线：**物理隔离**。

我创建了一个独立的静态库 `lib_db_core`，并制定了严格的隔离规则：

1. **对外（Header）**：只暴露纯 C++ 接口（`void*` 或 `std::unique_ptr<Impl>`），头文件中**绝对不包含**任何 `<pqxx/pqxx>`。
2. **对内（Implementation）**：在 `.cpp` 文件中包含 `pqxx`，利用 **PIMPL (Pointer to Implementation)** 模式隐藏底层实现。
3. **模块包装**：主项目的 `infra.db_adapter.cppm` 不再直接依赖 `libpqxx`，而是依赖这个干净的 `lib_db_core`。

### 3. 成果

这一改动彻底解决了困扰多时的 "INCLUDE-TRANSLATE" 编译错误。虽然增加了一层封装的复杂性，但保证了 C++ Modules 系统的纯净性和稳定性。

## 开发v5.0版本时的心得：业务闭环与真实数据

解决了架构和编译问题后，v5.0 终于可以专注于真正的业务逻辑了。

### 1. 解决 N+1 查询问题

在实现“查看课表”功能时，最初的想法是先查 `enrollments` 表，再循环查 `courses` 表。这在数据量大时效率极低。
我重写了 `StudentProxy::findSchedule`，利用 SQL 的 `JOIN` 语句一次性拉取学生关联的所有课程、教师和时间地点信息，将数据库压力降至最低。

### 2. 会话管理与鉴权

之前的系统登录只是简单的“角色选择”，没有任何安全性。
在这个版本中，我引入了 `users` 表和密码验证逻辑：

* 在 `SystemController` 中增加了 `login(id, password)`。
* 维护了一个 `m_currentUser` 会话上下文。
* 现在，只有登录为“TEACHER”角色的用户，才能执行“录入成绩”的操作，系统安全性得到了初步保障。

### 3. 数据一致性挑战

在测试中发现，内存中的对象状态（如 `Student` 对象里的课程列表）经常和数据库不一致。我重新设计了数据加载流程：**每次关键操作前，强制从数据库重新 hydrate（注水/加载）对象**，虽然牺牲了一点性能，但确保了数据的绝对准确，避免了并发操作下的脏读风险。

## 开发v6.0版本时的心得：交互体验与细节打磨

功能跑通了，但用起来很难受。v6.0 主要是在做“人用的系统”，而不是“机器跑的代码”。

### 1. 交互体验的“死穴”

在自动化测试（使用 `test_inputs.txt`）时，我发现了一个严重的 Bug：

* **死循环**：`showLoginMenu` 中移除了 `exit` 检测，导致用户（或测试脚本）无法正常退出程序，遇到文件结束符（EOF）时程序会陷入“输入不能为空”的无限循环。
* **解决**：在所有输入环节增加了对 `exit` / `q` 关键字的检测，允许用户随时中断操作或安全退出。

### 2. 也是架构思考：关于 Getter/Setter 的争论

在代码 Review 时，针对是否应该使用 `getStudentId()` 这种 Getter 方法产生了分歧。

* **观点**：过度使用 Getter 会破坏封装性，让对象变成单纯的数据结构。
* **调整**：我尝试减少 Getter 的使用，更多地通过“行为”来交互（例如 `student.isEnrolled(course)` 而不是获取 list 自己判断）。但在 CLI 打印报表时，Getter 又是必须的。最终达成妥协：**领域逻辑内部尽量少用 Getter，但 DTO（数据传输对象）和 UI 展示层允许使用。**

### 3. 真实数据的痛

为了验证系统的健壮性，我不再使用 `TEST_101` 这种假数据，而是硬编码录入了 42 门真实的大学课程数据。这立刻暴露了之前没发现的 UI 排版问题（课程名太长导致表格错位），随手修复了 `std::format` 的对齐参数。

### 4. 最终交付

至此，系统已经具备了完整的生命周期：从数据库底层隔离，到领域模型封装，再到 CLI 交互闭环。虽然过程曲折（特别是 GCC Modules 的坑），但最终实现了一个基于 C++23 标准的现代化选课系统。
